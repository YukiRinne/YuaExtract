# YuaExtract Native Hibiscus UI Architecture & Bridge Specification

## 1. Architecture Verdict

### 1.1 Core Verdict
We adopt **Win32 Native Host (`YuaExtract.exe`, x86/Win32, MSVC v143) + Embedded Microsoft Edge WebView2 (`ICoreWebView2` via static loader `WebView2LoaderStatic.lib`) + React 18 / TypeScript / Vite 5 Hibiscus Shell (`yua-shell`)**, backed by the existing, battle-tested C++ kernel modules (`YuaExtractHost`, `YuaExtractWorkspace`, `HashNameRestorer`, `HashNameMiner`, `ExtensionSet`, `OnlineUpdate`, and the injected 32-bit DLLs `CxdecExtractorUI.dll`, `CxdecExtractor.dll`, `CxdecStringDumper.dll`, `CxdecHashRestore.dll`, `CxdecKeyStatic.dll`, `CxdecRepacker.dll`, `CxdecPeUnpacker.dll`, `CxdecAntiMalform.dll`).

### 1.2 Trade-off & Compatibility Evaluation

| Dimension | Evaluation & Decision |
|---|---|
| **OS Support & Win7 SP1 Claim** | `README.md:36` notes the project retains `_WIN32_WINNT=0x0601` (Win7 SP1 target) while recommending Windows 10/11. By linking `WebView2LoaderStatic.lib` (x86), `YuaExtract.exe` imports zero Win10-only kernel symbols and loads on Win7 SP1+ (working with WebView2 Runtime 109 on Win7/8.1 or Evergreen on Win10/11). If WebView2 Runtime is absent or `--legacy-win32` is passed, `YuaExtract.exe` **never** falls back to mock data: it displays a fail-closed native diagnostic dialog with offline runtime guidance and an explicit user option to launch the retained Win32 fallback window (`RunLegacyWin32MainWindow`). |
| **Bitness (`Win32 / x86`)** | Target KiriKiri Z / Hxv4 / CxdecV2 games are 32-bit x86 executables. Detours DLL injection (`StartGameAndInjectDll`) requires a 32-bit loader. `YuaExtract.exe` remains strictly `Win32` (`x86`), using the 32-bit WebView2 loader (`x86\WebView2LoaderStatic.lib`) which connects to the system's x86 `EmbeddedBrowserWebView.dll`. |
| **COM STA & Thread Affinity** | WebView2 requires a Single-Threaded Apartment (`CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED)`) on the UI thread. **All `ICoreWebView2` / `ICoreWebView2Controller` calls are strictly confined to the main Win32 UI thread (`WindowProc`).** Background worker threads (Restore pool, Supplement Miner, ExtensionSet Generate/StaticHash/DryRun, OnlineUpdate FetchIndex/Download, Collect log poller, Batch XP3 monitor) never touch COM/WebView objects directly; they enqueue structured JSON events under a `CRITICAL_SECTION` and `PostMessageW(hwnd, kMsgWebViewPush, ...)` to marshal delivery onto the UI thread. |
| **Local Asset Serving & Origin Lockdown** | Production builds compile `yua-shell` into `<LoaderDir>\shell\`. WebView2 maps virtual host `https://yua.local/` to `<LoaderDir>\shell\` via `SetVirtualHostNameToFolderMapping(..., COREWEBVIEW2_HOST_RESOURCE_ACCESS_KIND_ALLOW)` (the `ALLOW` mapping applies to `https://yua.local/` only). Navigation, frame loading, `NewWindowRequested`, and `DownloadStarting` outside `https://yua.local/` are blocked (`put_Cancel(TRUE)`). |
| **Production vs. Mock / Test Isolation** | Production `vite build` never packages the mock: the `import("./mock/backend")` dynamic import sits inside a compile-time guard (`import.meta.env.DEV \|\| import.meta.env.MODE === "demo" \|\| import.meta.env.MODE === "test"`) that folds to `false` when `MODE=production`, so `backend-*.js` is tree-shaken out of `shell/assets/`, and `window.__YUA_SHOT__` / `failDemo` registrations are stripped from the bundle. There is no `?mock=1` flag; only `?nomock=1` exists (to disable the mock in dev/demo/test builds). If `window.chrome?.webview` is unavailable, the UI renders a fail-closed diagnostic screen rather than simulating success. |
| **Task Lifecycle & Concurrency Safety** | Every asynchronous operation carries a monotonic `jobId` (and restore runs carry an independent `restoreSessionId` + per-pack `RestoreTask` state). Progress updates are throttled (100 ms interval) so Windows message queues and React renders are never flooded, while terminal states (`done`, `failed`, `cancelled`, `success`, `error`) bypass throttling and are guaranteed to arrive. `RestoreOverlay` Start/Stop state is governed by active restore session/tasks rather than a single global `job.kind` slot. |

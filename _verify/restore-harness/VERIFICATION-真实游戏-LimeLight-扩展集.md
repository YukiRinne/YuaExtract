### 1.1 为什么用**沙箱工作区**

产品的「工作区 = 目标游戏所在目录」，输出目录名是固定的（`Extractor_Output` /
`Restored_Extractor_Output` / `StaticHash_Output` / `ExtensionDraft`）。
为了**不动用户的真实游戏目录**，本轮把游戏文件复制成一个隔离沙箱，让产品在沙箱里跑：

```text
_verify\realgame-test\                （本报告写成时在 _verify\restore-harness\Run\realgame\；
  App\      ← Release 的快照（YuaExtract.exe + CxdecExtractordll + Log）—— 独立工具目录，
              避免产品日志覆盖 Release\Log\RestoreDetail_*.txt（那批是上一轮的真值，绝不能被覆盖）
  ws\       ← 沙箱工作区（= 产品的"游戏目录"）：12 个 .xp3 + 两个 exe + Version.dll +
              plugin\ + ExtensionDraft\rules.int + StringHashDumper_Output\
  out\      ← 全部证据（控件清单 / 任务时间线 / 还原报告 / 对比明细）
```
> `App\` 与 `ws\`（约 21 GB）**已在收尾清理中删除**；`out\` 里可复算的大件
> （`StaticHash.lst`、`archive-dump.json`、枚举名单）也一并删了，留下的都是记录
> "产品当时到底做了什么"的小证据。要重跑用 `setup-sandbox.ps1` 重建 `App\` 与 `ws\`。

工具快照与仓库 `Release` 那份 **sha256 完全相同**（上表指纹），目标 exe 与真实游戏那份
**sha256 完全相同**（所以档案的 `exe 摘要命中` 判定是真的命中，不是碰巧）。

**真实游戏目录全程只读**，收尾复核（§6.3）确认：`ExtensionDraft` / `Extractor_Output` /

## 5. 发现（均为「轻」，不影响输出正确性）

### 5.1 模式1 步骤2 **仍然要启动游戏**（口径，非缺陷）

实测点了「步骤2：提取动态 XP3 资源」之后：产品把目标切到 `limelight_lj_crack.exe`、
**启动游戏**、注入 `Cxdec Batch Extractor` 解包窗口（窗口在游戏进程里，
按钮 `Add Files` / `Clear Done` / 输出目录 / 开始），状态栏写「已启动游戏并注入解包界面」，
下一步提示「启动游戏后在解包窗口拖入 *.xp3」。

这与设计 §7 一致（模式1 步骤2 = 传统模式步骤1 同一件事），也与交接说明「模式1 = 把『跑游戏
动态采集』那一步换成『从扩展集生成静态 Hash 表』」一致 —— **免的是"跑游戏采哈希"，不是"解包"**。
本轮实际解包用上一轮同一份 `Extractor_Output` 预置代替（项目自带 mode1 脚手架也是这么做的，
目的正是让「动态 vs 静态」两次还原的输入完全相同）。**没有把 7.22 GB XP3 真的重解一遍**。

### 5.2 「生成」必须先手工填会社 —— 但会先拒绝并给出正确指引

在一个**没有**已填会社的工作区里点「生成当前游戏扩展集」，产品**明确拒绝**：

> 还没有填「会社」。会社是扩展集库的第一级目录，必须手工填（工具不猜）。
> 先点「编辑当前扩展集信息」填好会社与游戏名称，再生成。

行为正确（不猜、不静默），且「编辑扩展集信息」弹窗会**从现有 `rules.int` 的 META 预填**，
所以对已有档案的游戏只是"点两下"的事。**注意**：编辑只改内存 Meta，
所以「编辑 + 生成」**必须在同一个进程会话里**完成，关掉程序就没了（弹窗自己也这么提示）。

### 5.3 重新生成时 `META.generatedAt` 沿用旧值（信息性）

同一沙箱重跑生成，档案逐字节相同 —— 也就是说 `generatedAt` 仍是**上一次**的值
（`2026-10-15 14:52:34`），而不是本次生成时刻（15:40）。
好处是顺带让 E-7「字节可复现」通过；代价是 `info.txt` 的「生成时间」在重复生成后会**偏旧**。
不是缺陷（设计 §13.4 只说 UI 填 `generatedAt`，没规定每次重新盖章），
但如果日后想让「生成时间」反映最近一次生成，需要在生成路径上强制重写该字段
（注意这会让 E-7 的「逐字节相同」不再成立，要改成「除 `META.generatedAt` 外逐 chunk 一致」）。

### 5.4 「选择测试来源目录」的文件夹选择框脚本化很难（脚手架侧，非产品）

干跑默认的「测试来源目录」= 采集来源目录 = `<工作区>\Restored_Extractor_Output`。
本轮先按真实用户姿势用「选择测试来源目录」(4110) 覆盖它，弹出的
`IFileDialog` 是 `#32770` + `DUIViewWndClassName` + `文件夹:` Static(1090) + Edit(1152) +
`选择文件夹`(id=1)。**写进 Edit(1152) 再点「选择文件夹」并不生效** —— 交回去的仍是对话框
**当前所在目录**（即使补发回车也一样），结果第一次干跑扫的是当时对话框停留的目录（真实游戏目录）。
**这是驱动侧的限制，不是产品缺陷**（人工点击完全正常）。

## 7. 限制 / 本轮没做的事

1. **步骤2 没有真解包 7.22 GB XP3**（见 §5.1）：用的是上一轮同一份 `Extractor_Output`。
   真解包在游戏内 `Cxdec Batch Extractor` 里做（`Add Files` + 开始），本轮没有驱动它。

3. **没测第三方扩展集**（别的盐的档案）：E-4「坏档案必须被拒」在合成夹具上已有 7 条用例，
   真实数据这边只测了**本作自己的档案**（`exe 摘要命中` 这一档）。**`盐一致但 exe 不同`**
   与 **`盐不同/拒绝`** 两档没有真实数据样本可造。
4. **没测多会社/多作品库、库根不可写（`Program Files`）**（交接说明 §7 #9 仍待办）。
5. **`WM_SIZE` / 多显示器 / 不同 DPI 的像素口径**未涉及（与 R-8 同一条边界）。
6. **沙箱当时占约 21 GB**（`ws` = 7.22 GB xp3 + 7.31 GB 解包 + 6.60 GB 还原）。
   **已在收尾清理中删除**（连同 `_verify\restore-harness\Run\` 整个脚手架临时目录）；
   要重跑：`setup-sandbox.ps1` 重建 `App\` 与 `ws\`，再按 §6.2 分步驱动。

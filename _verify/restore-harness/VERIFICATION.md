   把 `缺目录 Hash 3` 一起排掉，与实现的缩进格式无关。已改成只排除"以目录/路径结尾"的表头行，

## E. 第二轮暴露并修掉的**脚手架**缺陷（产品无责，记录备查）

1. **压力夹具的类别标签是错的**：`missing-dir` 那批文件复用了**已映射**的目录哈希
   → 它们其实完全可还原 → 实现正常还原，断言反而判它不合格（实测输出 51,025 而非 42,024）。
   修法：缺的那一半改用真正不在映射表里的哈希；并在生成器里加了**夹具自检**
   （逐条核对"类别"与"映射表实际内容"一致，不一致直接抛错），这类错误以后不会再静默通过。
2. **`-f` 与除号的优先级**：`"...{0:N0}..." -f $ms / 1000, $a, $b` 会被解析成
   `(fmt -f ($ms/1000)), $a, $b` → 报 "Index must be ... size of the argument list"。
   小用例只跑 4 秒、这行 5 秒才打印一次，所以一直没暴露；压力用例一跑就崩。已加括号。
3. **数组返回值的嵌套陷阱**：`return ,$arr` 遇到调用方 `@(...)` 会被套成"1 个元素的数组"，
   `Where-Object` 只看到一条（实测 6 个已还原文件被当成 1 个）。已改回普通数组返回 + 调用方 `@()`。
4. **大用例的性能取舍**：6 万文件时逐条 `ConvertTo-Json` / 逐文件 `Get-FileHash` 要几十分钟；
   现在清单与输出列表走 TSV、目录比对走"排序行摘要"、遍历与哈希走 C# 批量接口
   （`Harness.Batch`）。另外发现 10 万次文件 open 会被杀软拖成几分钟，
   所以源目录摘要默认在文件数 > 5000 时不再做内容哈希（验收口径是"文件数与时间戳未变"，够用）。
5. 界面探测延迟取的是 `SendMessageTimeoutW(WM_NULL)` 的往返时间 —— 这是"界面有没有被
   进度消息打满"的量化依据（压力用例：0 次超时、最大 392 ms）。

## 6. 本轮暴露并修掉的**脚手架**问题（产品无责，逐条留痕）

这一轮脚手架自己出的问题比产品多，全部记下来以免下次重犯：

1. **完成判定被自己截断**：挖掘是独立阶段，标题早就显示"完成 4 / 运行中 0"、输出目录也不再变化，
   但挖掘还在跑。第一版据此宣布完成 → 规模档只量到 4 秒（其实跑了 90 秒）。
   现在必须**等到挖掘的结束标记**（`试算 … / 命中` / `第二遍` / `后映射`）才算跑完。
2. **把"功能说明"当成"挖掘开始"**：产品在窗口初始化时写了一段说明（"勾「推理补充还原」会……挖候选名……"），
   没勾选时也照样出现。我拿它当挖掘开始 → 未勾选的用例一直等一个永远不会来的结束标记，
   空等到 600 秒超时。现在只认"真的在挖"的行（`开始从游戏资源里挖掘候选名` / `挖掘中：扫描` / 第二遍）。
3. **O(n²) 空转（lead 杀掉的那次）**：规模档的独立枚举里，对每个源文件去 2 万个名字里线性找一遍
   = 20004 × 20004 ≈ **4 亿次比较**，纯内存所以磁盘毫无增长、单核 99% CPU，看起来就是"卡死"。
   现在两张表（`sourceRel→expectedRel`、`leaf→输出项`）先建好，循环内只做 O(1) 查找：
   同一件事从 **>10 分钟**变成 **24 秒**。同类问题还有两处一并修了（名字表逐名字全表扫、
   输出清单用 `+=` 累加）。
4. **线程采样没 `Refresh`**：`Process.Threads` 读的是缓存，一直显示"9 → 9"（看不出回收）。
   加 `$process.Refresh()` 后与实现者实测一致：**9 → 4**。
5. **T-2 的语义**（两次踩）：关还原窗口 = 中止还原并**回到主窗口**，进程本来就该活着；
   而且确认框按钮文案是 `是(&Y)`/`否(&N)`，精确比较 `'是'` 永远匹配不上（曾出现"识别到 224 次、点击 0 次"）。
   现在先归一化再比、匹配不上用 `PostCommand(IDYES)` 兜底，判定改为"窗口消失 + 线程回收 + 关主窗口后干净退出"。
6. **X-2 自己也犯了第 2 条的错**：拿"日志里有没有挖掘字样"当判据 → 未勾选也报失败。
   现在只认"真的在挖"的痕迹 + run JSON 里的 `miningStarted`。
7. **千位分隔符**：产品用带逗号的数字（`20,012`），我的正则 `(\d+)` 匹配不上 → 明明日志里有那一行却说"没有"。
   现在数字段统一 `([0-9][0-9,]*)` 再 `-replace ',',''`。
8. **大夹具的清单在 TSV 里**：条目 > 5000 时 `manifest.json` 不带 `files` 数组，
   我却从 `files` 读 → 独立枚举数出 0/0，冤枉了实现。现在走 `Get-ManifestFiles`（自动回退 TSV），
   并把"枚举对象（源清单 + 输出目录的绝对路径）"打进断言详情自证。

性能护栏（防止再出现"静默空转"）：每个断言段落都打印 `[assert <耗时>ms] <在做什么>`；
大循环带迭代上限（超过直接判失败而不是空转）；脚本末尾的 **X-6** 会统计"整脚本耗时 + 最长 5 段"，
任何一段超过 120 秒就判失败并点名。断言详情也做了限流（命中上万时只逐条列前 10 个，
否则 checks JSON 会涨到 6.5 MB —— 现在规模档的 checks JSON 是 **14 KB**）。

## 7. 覆盖不到的地方（如实记录）

- **真实游戏数据**：按 lead 要求没有碰用户游戏目录，因此"命中 5.1 万 / 60,146 文件"这一档
  是用**合成 2 万命中 + 3M 候选**覆盖的（同量级）；真实数据上的命中率与耗时未复测。
- **工具提示**：只做了静态字面量扫描（工具提示文案就是字符串字面量，已被 27 处那轮覆盖），
  没有做"鼠标悬停读 tooltip"的运行时验证。
- **`__dupN` 回归**：补充还原夹具里没有重名源，X-3 只能证明"没有膨胀"；
  重名冲突本身的正确性由 A-10（小用例）覆盖。
- 像素级界面差异、真实游戏注入后的挂钩路径不在本轮范围。

## 8. 裁决

- **产品侧：无缺陷**。lead 提到的两条"失败"经复核都是脚手架侧（千位分隔符、独立枚举读错来源），
  已在 §6 第 7、8 条修掉并重跑通过；其余 18 条断言在夹具档与规模档双双通过。
- 已知小瑕疵（复选框创建处的老注释与现行文案矛盾）按"注释一律不动"保留，不计缺陷。

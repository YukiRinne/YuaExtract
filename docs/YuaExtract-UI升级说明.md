# YuaExtract 界面升级说明

上游项目 **KrkrExtractForCxdecV2Extra** 的功能全部保留，界面重做成我们自己的 **YuaExtract**，
并把"解包 → 收集 Hash → 还原资源名"这条主线做成三步流程。

## 3. 三步流程各自做了什么

### 步骤1 · 提取动态 XP3 资源
启动游戏并注入 `CxdecExtractorUI.dll`（上游的批量解包界面）。游戏里把 `*.xp3`
拖进那个窗口排队即可，结果写 `Extractor_Output`。本窗口**不再自动关闭**——
上游老流程注入后就把 loader 关掉，现在主界面要留着承接步骤2、步骤3。

#### 启动前的那道闸门（点一次按钮就要真的启动起来）
上游的 `RunSteamStubPrecheck` **不是**"看一眼有没有壳"，它会真的动手：复制工作副本、
注入 `CxdecAntiMalform.dll`、跑一遍目标，把补丁结果写成 `<原名>_crack.exe`。
退出码约定（见 `CxdecAntiMalform/runtime_hook.cpp`）：`0` = 补丁已应用并写出成品，
`2` = 这个 exe 无需处理（典型情况就是上一趟的 `_crack.exe` 又被拿回来用），`3` = 需要补但没补上。

老界面里只能拖拽，所以上游的处理是弹一句「已生成 `_crack.exe`，请把它拖到本程序上继续」，
让用户手动再走一遍。在 YuaExtract 里这一步没有必要，但**第一版没做自动化**，结果是：

- 用户选好游戏、点「步骤1」，看到的是一个"请把 _crack.exe 拖回来"的框，游戏并没有启动 ——
  看起来就像按钮坏了。

现在的做法（`EnsureTargetReadyForLaunch`）：

1. 先把状态写进面板并强制重绘（"正在检查目标（反篡改补丁流程）……"），避免这几秒没有任何反馈；
2. 跑补丁流程；
3. 返回 false（退出码 2/3）→ 按上游语义直接继续启动；
4. 返回 true 且**产出了 `_crack.exe`** → **自动把目标换成 `_crack.exe` 并继续启动**，
   省掉手动拖回来那一步；界面与日志都会写明换了哪个文件；
5. 返回 true 但没产出（用户取消了脱壳确认 / 目标不是这个引擎的游戏）→ 中止本次启动并说明原因。

同时把上游那个"请把它拖到本程序上继续"的弹框去掉了（改成日志一行）——
既然已经自动接上，再提示用户手动拖回来就是多余且自相矛盾的。

另外：点步骤按钮时如果还没选目标，会直接把选择框弹出来，不需要先去点「选择」。

### 步骤2 · 加载动态Hash收集模块（只收集配对，**不还原**）
启动游戏并注入 `CxdecStringDumper.dll`，注入时设置 `CXDEC_HASH_COLLECT_ONLY=1`。
模块据此启动**收集控制台**（窗口类 `CxdecHashCollectConsole`，标题「YuaExtract 动态 Hash 收集控制台」）。
它**只收集"哈希名 ↔ 真名"的配对，一个文件名都不改** —— 还原全部交给步骤3。

```text
产物  <工作区>\StringHashDumper_Output\DirectoryHash.log   目录名 ↔ 目录哈希
      <工作区>\StringHashDumper_Output\FileNameHash.log    文件名 ↔ 文件哈希
```

控制台包含：状态信息（游戏路径 / 工作区 / 分母目录 / PID / 运行时间）、两条收集进度条
（DirectoryHash、FileNameHash，各显示 `已收集 / 目标总数 百分比`）、资源还原率、
两个实时日志页签（滚动显示新增的 `名字##YSig##哈希` 行）、底部按钮
（启动游戏〔禁用并给出提示〕/ 关闭游戏 / 清空目录文件 / 打开输出目录 / 返回主界面）。

进度口径：**分母** = 启动时扫一遍纯 Hash 目录（`CXDEC_RUNTIME_HASH_TARGET_DIR`，取不到退回
`<游戏目录>\Extractor_Output`）得到的**去重** 16 位目录哈希数与 64 位文件哈希数；
**分子** = 两份映射日志里**命中该集合**的去重哈希数。取交集是为了不把"游戏加载了、
但这份解包产物里没有"的条目算进去 —— 所以这个百分比的真实含义是
「这份解包产物里已有多少比例的资源拿到了真名」。

这一步**不写** `RuntimeHashRestore.log`、**不碰**纯 Hash 目录里任何文件名。
不带该环境变量时仍走上游 `RuntimeHashUI`（边收集边就地还原），回归路径原样保留。

### 步骤3 · 用动态Hash还原资源名
**纯离线**，不碰游戏进程。点主界面「步骤3」打开**独立的还原窗口**
（窗口类 `YuaExtractRestoreWindow`，非阻塞、单例，重复点击只把它置前）。
窗口自己按**一个封包一个任务**排队，用 N 个工作线程（默认 4）并发还原：

```text
输入  <工作区>\Extractor_Output          解包结果（<包名>\<目录Hash16>\<文件Hash64>）
      <工作区>\StringHashDumper_Output   DirectoryHash.log / FileNameHash.log
                                         以及该目录下所有 *.lst（HASH:name）
输出  <工作区>\Restored_Extractor_Output  **只保留已还原的文件**
      <工作区>\Restored_Extractor_Output\RestoreReport.txt
```

窗口包含：还原输出目录 + 工作线程数、`总任务 / 运行中 / 排队 / 完成 / 失败` 统计、详细日志、
任务概览列表（列：封包 / 状态 / 进度 / 当前条目 / 详细信息）、两个复选框、
底部按钮（开始 / 打开还原目录 / 返回主程序）。

**默认只留已还原的文件**（复选框一「保留未还原文件名的文件（文件后缀已确定）」默认不勾）：

| 情况 | 文件名字段 | 目录字段 | 默认（不勾） | 勾选保留 |
|---|---|---|---|---|
| 完全还原 | 真名 | 真名 | 输出 | 输出 |
| 缺目录名 | 真名 | Hash | 不输出 | 输出（保留 Hash 目录名） |
| 缺文件名 | Hash | 真名 | 不输出 | 输出 |
| 都缺 | Hash | Hash | 不输出 | 输出 |
| 本来就是明文（`.alst` 清单等） | 真名 | 真名 | **输出** | 输出 |
| 明文名但在 Hash 目录下 | 真名 | Hash | 不输出 | 输出 |

判据是「**最终目标路径里还有没有未解析的 Hash 段**」，而不是「名字有没有被替换过」——
否则 `.alst` 这类本来就叫这个名字的文件会被误丢。

复选框二「推理补充还原（从游戏资源中挖掘候选名，哈希验证后写入）」是**真功能**，默认不勾。
勾上后是**两遍式**：先只用步骤2 收集的映射做一遍普通还原，跑完再挖掘候选名补漏（见下）。

### 未还原文件按文件头补后缀（勾选复选框一后生效）

未还原、但勾了「保留」的文件，不再是无后缀的 `<64位Hash>`，而是由文件头判定补上后缀：

| 文件头 | 后缀 | 文件头 | 后缀 |
|---|---|---|---|
| `\x89PNG` | `.png` | `OggS` | `.ogg` |
| `\xFF\xD8\xFF` | `.jpg` | `TLG` | `.tlg` |
| `PSB\0` | `.psb` | `RIFF` | `.wav` |
| `BM` | `.bmp` | `PK\x03\x04` | `.zip` |
| `7z\xBC\xAF` | `.7z` | 可打印占比 ≥90% | `.txt` |
| 都不是 | `.bin` | | |

只读源文件头、只改输出目录里的名字，源目录不动。报告里多一行「按文件头补后缀 N 个」。
补后缀前先剥掉解包器已经写上的后缀，避免 `<hash>.png.png`。识别不出就落 `.bin`——
宁可给个通用后缀，也不让文件没有后缀（那 Windows 就打不开了）。

### 推理补充还原（候选挖掘）

勾选复选框二后，整个还原分**两遍**，挖掘夹在中间：

1. **第一遍：普通还原** —— 只用步骤2 收集的映射还原，不挖掘。跑完在详细日志里报一次还原率。
2. **挖掘**（跑在**后台线程**，`BELOW_NORMAL` 优先级，界面全程可正常操作）：
   - 读 `Log\Universal.log` 里的 `Hash Seed` / `FileNameHasherSalt`。**读不到就明确报错**
     「请先执行一次步骤2」，绝不静默跳过（此时只做第一遍，流程照常收尾）。
   - 扫源解包目录里的**非二进制包**（排除 `voice/voice2/video`；文件头是图片/音频/压缩包
     魔数的单个文件也跳过），按 UTF-8 解码抓「像资源名」的串（含结构字符：数字/下划线/点/横线，
     长度 2..48）。
   - 每个候选：`BLAKE2s-256(key=FileNameHasherSalt, UTF16LE(裸名+扩展名+seed))` 算哈希，
     与磁盘上仍是 64 位 Hash 名的文件集合求交 —— **命中才写进映射表，一条都不自己造**。
   - 命中结果并入本次映射表（运行时收集到的条目优先，不覆盖），并落盘到
     `StringHashDumper_Output\MinedNames.lst`（与已有内容去重合并）。
3. **第二遍：补漏** —— 用补全后的映射再跑一遍，**只处理第一遍没交付的文件**（已交付的直接跳过，
   不重复复制、不造 `__dupN`）。勾了「保留」时，第一遍以 `<哈希><补的后缀>` 交付的文件，
   这一遍挖出真名后会换成真名、并删掉那份哈希名残留。

**这不是猜**：候选名只是"线索"，最后一步是哈希相等，所以最坏情况是补不上，不会补错。

挖掘期间窗口详细日志实时显示「扫描 X 个文件 / 候选 Y / 命中 Z」；结束时给出两行还原率
（口径＝**已还原 ÷ 哈希名文件数**，两位小数）：

```text
第一遍普通还原：已还原 55,000 / 60,133（91.46%）
还原率 97.66%（已还原 58,715 / 哈希名文件 60,133，推理补充还原新增 3,715）
```

未勾选复选框二（单遍）时只出最终一行、且不带「新增」部分：
`还原率 91.46%（已还原 55,000 / 哈希名文件 60,133）`。
挖掘跑在后台线程（`BELOW_NORMAL`），所以**界面不会卡**（历史版本曾在界面线程同步挖，导致数分钟无响应）。

**三个前提**：① 至少跑过一次步骤2（有 `Hash Seed`）；② 游戏把资源名以明文存在资源里
（本作 PSB + UTF-8 明文，收益大；TJS 字节码/压缩资源的游戏收益小得多）；③ 步骤1 已解包。

多线程下任务终态由**工作线程**按还原返回值**先写进任务记录**、再发通知消息；
界面重画时读的是任务记录。所以即便一条进度消息都没送到，也不会出现
"任务永远停在处理中"（这正是 `CxdecExtractorUI` 踩过的坑，见 §6.5）。

实现口径与运行时恢复模块（`HashRestoreUI.cpp`）严格对齐：

- 映射解析：`真名##YSig##HASH`（UTF-16）与 `HASH:name`（UTF-8）两种格式；
  16 位 hex 视为目录 Hash（`/`、`%EmptyString%` 都是根域），64 位 hex 视为文件 Hash；
  目录分隔符统一 `\`，结尾分隔符去掉。
- 候选表 `dirs_*.txt` / `files_*.txt` 是"名字清单"不是映射表，按文件名排除，
  免得被当成畸形映射读一遍。
- 目标路径 = `<包名>\<明文目录>\<明文文件名>`；目录名为空（根域）时直接落在包目录下。
- 重名落 `__dupN`，不覆盖已有结果（所以对同一个输出目录重跑一次会得到 `__dup1` 副本，
  而不是覆盖 —— 想重跑请先删掉输出目录）。
- **缺映射的文件默认不落盘**（连它是哪个包、哪个 Hash 都记进报告），报告里分
  `缺目录 Hash` 与 `缺文件 Hash` 两类计数 —— 这两类的补法完全不同；
  勾选「保留未还原文件名的文件」后才照原样复制（保留 Hash 路径）。
- `Extractor_Log` / `ExtractLog` 目录跳过，不跟着还原、不计入统计。
- 非哈希名文件（`.alst` 清单等）**始终原样复制**（它们本来就叫这个名字，不属于"未还原"），
  保证还原目录仍能直接喂给重封包。

与运行时恢复**唯一的、有意的差别**：这里**复制**而不是就地移动。
源解包目录保持可重跑，补完映射再跑一次即可，不会留下半还原的现场。

顺带一个符合我们之前讨论的设计：`StringHashDumper_Output` 里**所有 `*.lst` 都会被读**，
所以"每游戏攒一份对照文件"的成果，只要丢进那个目录就能被步骤3 用上，不用改代码。

### 6.5 批量解包界面"卡在处理中"的修复与验证

**现象**（用户实际遇到）：12 个包里 11 个显示已完成，最后 `voice2.xp3` 一行永远停在
"处理中 100%"，看起来像卡死。

**诊断**（用日志对账，不是猜）：

```text
Log\Extractor.log    23:46:46  Extract Completed: voice2.xp3      ← 解包器早就收工了
                      voice2 目录 7096 个文件、voice2.alst 7097 行（7097−1 个跳过占位）
Log\ExtractorUI.log  23:46:53  #12 state=3 current=7097 total=7097 ← 最后一条进度，之后无 state=4
```

把两边的数量对起来就清楚了：本次应投递 `2 × 60145 = 120290` 条进度，界面只收到
**54809 条，丢了 54.4%**，其中恰好包括 `voice2.xp3` 的收尾状态。

根因在 `PostTaskUpdate`：进度用 `HeapAlloc + PostMessageW` 投递，**投递失败就静默丢弃**；
而解包器每个文件发两条，一个 48324 文件的包就是近 10 万条消息。实测本机
`PostMessage` 队列上限恰好是 **10000** 条（用 `PostThreadMessage` 灌满测得），
120290 条是这个上限的 12 倍 —— 必然大量丢弃。

**修复**（都是小改，共 4 处）：

| 改动 | 作用 |
|---|---|
| `Extracting` 类更新按 100ms 节流（准备/索引/完成/失败无条件投递） | 14196 条 → 个位数，队列不可能再打满；顺带把 9.2 MB 的 UI 日志压下去 |
| 工作线程在 `ExtractPackageEx` 返回后按返回值补一条收尾状态 | 高频进度可以丢，**任务的收尾不能丢**；即使解包器那条丢了，行也会正确收尾 |
| 关键状态投递失败时重试（最多 50×1ms） | 兜底消息自己也不会丢 |
| 界面侧幂等处理 | 兜底消息带 0/0，不覆盖已收到的真实进度；已完成时进度显示成 100%；不用兜底文案盖掉解包器给的失败原因 |

**验证**：搭了一个假引擎（`_verify\harness\FakeCore.cpp`，复刻 7097 条目 / 14196 条更新的规模），
配上**真实的 UI DLL** 跑完整链路，用同一个用例对"修复前 / 修复后"做对照：

| 用例 | UI DLL | 列表状态 | 进度 | 标题 | 投递条数 | 判定 |
|---|---|---|---|---|---|---|
| 正常 | 修复后 | **已完成** | 100% | 完成 1 | 5 | 通过 |

**弹窗**：不是 .rc 对话框 —— 与图2 同一手法，注册顶层窗口类 `YuaExtractOnlineDialog`（标题「在线更新扩展集」），
用 `FindWindowW(L"YuaExtractOnlineDialog", nullptr)` 定位后 `GetDlgItem` 取件。

| 控件 | ID | 说明 |
|---|---|---|
| 「仓库地址」（EDIT） | 4140 | **必须显示当前基址**；离开输入框或点动作按钮时回写配置 |
| 「拉取索引」（BUTTON） | 4141 | 拉 `index.txt` |
| 列表 (LISTBOX) | 4142 | 一行 = `会社 / 作品 / 条数 / 状态` |
| 「下载并安装选中」（BUTTON） | 4143 | 下载 → 校验 → 入库 |
| 进度条 | 4144 | 0..100 |
| 状态文字（只读多行 EDIT） | 4145 | 阶段 / 结果 / 明确原因 |
| 「关闭」（BUTTON） | 4146 | 关窗前**先中止线程**再销毁窗口 |

**闭环**：拉索引 → 与本地库算差异 → 下载 → 校验 → 入库（随后重扫列表与主界面）。

- 联网动作（拉索引 / 下载）跑在**后台线程**（`BELOW_NORMAL` 优先级），进度走私有消息；
  一次连接超时就是几十秒，**绝不在界面线程里同步联网**。
- 下载线程**不做入库**：入库前可能要问用户"要不要覆盖本地那份"，而确认框是模态的 ——
  在线程里弹模态框会把线程卡在 UI 里，进度与取消全乱套。所以线程只做"拿到字节 + 校验"，
  决策与入库回界面线程。
- 暂存目录 `<工具目录>\Log\OnlineStaging`（工具目录不可写时退 `%TEMP%\YuaExtract\OnlineStaging`），
  校验失败与入库成功后都尽力删干净。

**索引就是一份 `manifest.txt`**（同 10 列 TSV），远端仓库布局与本地库**同构**
（`<会社>/<作品>/rules.int` ↔ `<工具目录>\ExtensionLibrary\<会社>\<作品>\rules.int`），
所以**没有新格式、没有 JSON 解析器**。逐列定义见 [`扩展集设计.md`](扩展集设计.md) §14.3。

**四种状态**（`Online::Classify`；列表与总结论共用同一份结果，不各算一遍 —— 两处口径分叉的话，
"列表写着新增、结论却说更新"立刻就会出现）：

| 状态 | 判据 | 列表上的措辞 |
|---|---|---|
| 新增 | 本地既没有同一「会社/作品」槽位、也没有同一目标 exe 摘要的条目 | `新增（本地还没有）` |
| 已是同一份 | 本地已有，且**档案摘要相同** | `已是最新（档案摘要与本地相同）` |
| 可更新 | 本地已有、档案摘要不同，且远端条数 **≥** 本地最全的那条 | `可更新（档案摘要不同，且条数不少于本地）` |
| 本地更全 | 本地已有、档案摘要不同，且远端条数**少于**本地最全的那条 | `本地更全（条数比远端多）—— 覆盖会减少覆盖度，默认不覆盖` |

- 「已是同一份」**直接跳过下载**：再下一遍一模一样的字节、再覆盖一遍，本地什么都不会变。
- 「可更新」与「本地更全」在入库前**先弹确认框**，列出本地 / 远端各自的条数与档案摘要；
  「本地更全」额外写明"覆盖之后本地能解出的名字会变少"。点「否」= 本地保持原样，暂存文件照旧清掉。
- 入库复用内核既有的 `ExtensionSet::InstallToLibrary`，本层不再包一层同义函数。

**信任链 9 条**（原表见 [`扩展集设计.md`](扩展集设计.md) §14.4，下边是给人看的版本）：

| # | 要求 |
|---|---|
| 1 | 仅 `https`；**不跟随重定向**（首跳 https、次跳 http 一样能把明文灌进来）；连接 / 发送 / 接收**各自**超时（10 / 15 / 30 秒）；索引 ≤ 4 MB、档案 ≤ 64 MB；UA 标注产品名与版本 |
| 2 | 下载后 **sha256 必须等于索引里的 `档案摘要`** —— 把"下到的字节"钉死在索引上 |
| 3 | 解码档案（走内核既有解码路径）→ magic / version / headerSize / CRC32 / chunk 结构必须全部通过 |
| 4 | 解码出的内嵌 `target.sha256` 必须等于**索引里的** `目标exe摘要` —— 拿**索引**当信任根，不拿本机 exe 当根 |
| 5 | 档案**自洽性**：`EXCEPTIONS` 必须为 0；用内嵌盐展开后「好哈希 → 名字」的条数必须与 `STATS` 里的目录/文件条数一致（防截断、防名字列表被改短） |
| 6 | 以上任一不过 → **明确报错、丢弃临时文件、本地一个字节都不改**（**含新建的目录**：失败后磁盘必须与调用前逐项一致，空目录也算）。**例外要如实说破**：如果 `rules.int` 已经被写进库之后才失败（清单读不到/写不了），无法恢复原状 —— 那时错误里必须明写「本地库与操作前**不一致**」，界面**不许**再说"未被改动" |
| 7 | 入库复用 `InstallToLibrary`；同 exe 摘要但档案摘要不同时**先给确认**（列出新旧条数 / 摘要），不静默覆盖 |
| 8 | **绝不自动加载、绝不后台联网**：只在用户点「在线更新」时拉一次；入库只写库，用不用仍由归属校验（设计 §2.1）把关 |
| 9 | **索引行的 会社 / 作品 必须等于档案内嵌 META 的 会社 / 作品**（`_wcsicmp`），不一致 → 拒，错误点名两边。**2026-10-15 独立验证发现后补**：不加这条时，"安装槽位"会有两个名字来源 —— 产品按索引名弹「已新增 / 要覆盖的是 A/B」，而 `InstallToLibrary` 实际落到**档案 META 名**那个目录；覆盖确认框报给用户的条目与实际被替换的条目甚至可能不是一个。**索引是信任根，槽位必须可预测** |

**它兜不住什么（必须一起看）**：档案里**不存哈希层**（设计 §3.1 默认不存），本地**没有可对照的哈希**。
第 5 条那种"名字 + 盐 → 哈希算得回去"的自校验**只在生成时成立**（那时手里有动态采集到的哈希）；
**校验别人给的档案时根本验不了** —— 把某个名字改掉，本地没有任何依据能发现。
所以：**信任根就是索引**（第 2 条证明"下到的字节 = 索引里那一条"，第 3 / 5 条证明"这份字节自洽、没被截断"），
**工具不声称能验证"名字对不对"**，界面上也不这么说 —— 本页签右栏专门有一节「名字对不对，本工具验不了」，
「扩展集留言」弹窗末尾也带同一句。
名字的最终把关是**事实**：归于本作后用它还原，还原率不对就是不对；再退一步，用户可以对比条数。
**要更强的保证只能靠仓库侧签名，本轮不做。**

**基址可配置**：解析顺序（先命中先用）

1. 环境变量 `YUAEXT_ENDPOINT`
2. `YuaExtract.ini` 的 `[online] base=` —— 优先 `<工具目录>\YuaExtract.ini`；工具目录不可写时用
   `%LOCALAPPDATA%\YuaExtract\YuaExtract.ini`
3. 代码常量 `kDefaultRepositoryBase`（本轮 `<owner>/<repo>` 仍是**占位**，仓库建好后只改这一处）

弹窗里可以直接改并回写 ini；**弹窗必须显示当前基址**，否则"点了没反应却不知道在打哪个地址"；
回写失败时把输入框**还原成实际生效的基址**（显示一个没存进去的值比不改还糟）。
**为什么必须可配置**：`raw.githubusercontent.com` 在国内经常连不上或极慢 —— 这不是锦上添花，
是功能能不能用起来的前提（可换镜像 / jsDelivr / 自建）。

**失败口径**：端点不可达 / DNS 失败 / 超时 / 非 200 / 索引格式错 / sha256 不符 / 解码失败 / 自校验有例外，
**每一种各有各的措辞**，不许合并成"更新失败"一句；任何一种失败，
**本地库、库清单、工作区都必须与操作前逐字节相同**。成功的措辞要能区分「新增」与
「更新（覆盖了哪一条、旧档案摘要是什么）」。

**本轮不做**（照设计 §14.7）：

- 仓库侧写入（不做上传、不做 PR 流程），只读拉取
- 增量 / delta 更新（每次都整档下载；扩展集本来只有几百 KB）
- 冲突查看器（同一哈希多名字）
- 启动时自动检查更新、后台定时检查
- `<游戏目录>\User\<N>` 多工作区

### 7.4 运行环境自检（只读七项）

**为什么要有它**：这套工具对环境有四五处隐含要求，任何一处不对，表现出来的都是"点了某个按钮没反应"，
而症状离原因隔着好几个环节（比如"在线更新装不进去"其实可能是工具目录在 `Program Files` 下）。
一次列清楚，省掉一轮轮猜。

| # | 检查项 | 口径 |
|---|---|---|
| 1 | 工具目录可写 | 库默认就在它下面，写不了的话半条链都是死的；不可写则点名原因并给出路（把工具挪到可写目录） |
| 2 | Hash 收集模块 `CxdecStringDumper.dll` | 在不在 / 读不读得出 PE 头 / 是不是 32 位（`IMAGE_FILE_MACHINE_I386`）/ 记一行 SHA-256 摘要（**摘要只登记，不判对错**） |
| 3 | 扩展集库目录 | 未创建 = 提示级（一份都没装过就是这样，**不算错**）；存在则验可写 |
| 4 | 库清单 `manifest.txt` | 不存在 = 提示级（库是空的）；存在则真读字节，再交给内核同一份 `ParseManifestText` 解析（它就是在线索引那条路用的函数） |
| 5 | 库内每一份档案 | 逐份：文件在不在 / 能不能解码 / `EXCEPTIONS` 是否为 0 / 内嵌目标 exe 摘要是否非空。坏的点名是哪一份（前 5 条 + 总数） |
| 6 | 盐来源 `Log\Universal.log` 的 `Hash Seed:` | **只报告、不判错** —— 没有它时工具本来就会回落到静态派生（`ExtractKey_Output\Static`），那是一条正当路径，不是缺陷 |
| 7 | 总结论 | `全部正常` 或 `N 项问题`（`Severity == 1` 才算问题；提示级不计） |

**成功不弹模态框**（结论进右栏 + 日志一行，多行结论在日志里折成 ` / `），**失败才弹** ——
与干跑同一个口径：成功也弹的话，每点一次就要多点一次"确定"，很快就被无视了。

### 7.5 「扩展集留言」有两个，别混

这一条很容易混，所以单列：

| | 制作扩展集页签 · 图2 弹窗的「扩展集留言」 | 扩展集页签 · 「扩展集留言」按钮 (4136) |

## 8. 扩展集：一期已实现，二期预留

一期（2026-10-13）落地的是「**该作扩展集提取**」这条闭环，口径与格式见 [`扩展集设计.md`](扩展集设计.md)：

- **档案**：单一文件 `rules.int`（magic `'YXS1'` + chunk 表 + CRC32 + zlib），只存**名字**（目录 / 文件），
  哈希在加载时用**档案内嵌的盐**重算 —— 实测 20 条档案 734 B，名字层 12.7 字节/条。
- **制作扩展集页签**：生成（合并 `DirectoryHash.log` / `FileNameHash.log` / `MinedNames.lst` /
  `HashRestore_RecoveredNames.lst` / 其它 `*.lst` → 归一化 → **生成期自校验** → 落盘）、编辑信息（图2 弹窗）、
  测试（**只读干跑**出成功率）、安装到扩展集库（`<工具目录>\ExtensionLibrary\<会社>\<作品>\` + `manifest.txt`）。
- **首页模式1**：`该作扩展集提取` → ① 生成静态 Hash 表到 `StaticHash_Output` ② 提取动态 XP3 资源
  ③ 用静态 Hash 还原资源名（还原内核零改动，只换映射目录）。**全程不启动游戏。**
- **归属校验**：exe 摘要命中 → 直接用；摘要不中但盐一致 → 可用并标注；**盐不同 → 拒绝**；
  摘要不中又拿不到盐 → 默认拒绝，用户可显式"强行使用"（面板与日志**长期写明"未能校验归属"**）。

**2026-10-15 补上两件原先列在二期的**：`扩展集` 页签（浏览 / 打开 / 留言 / 环境自检，见 §7.1–§7.2、§7.4–§7.5）；
**分享 / 导入他人扩展集**以**只读在线更新**的形式落地 —— 只从远端独立仓库拉取（发现 → 校验 → 入库），
**不做上传、不做仓库侧写入**（见 §7.3）。「套用」这一半仍在首页（`该作扩展集提取`），本页签只到"装进库"为止。

**仍是预留（二期）**：

- `该会社合集撞新作`：跨作品复用只能走**名字**（哈希不可移植），需要按名字用新作的盐重算 +
  **目录侧 SipHash 撞库**；`rules.int` 已预留 `RULES` chunk（L1 规则层，语音批量命名也落这里）。
- 冲突查看器（同一哈希多名字）、`<游戏目录>\User\<N>` 多工作区、仓库侧写入 / 签名（上传、PR 流程、增量更新一并见 §7.3 的"本轮不做"）。
- 对照文件/词库的接入点仍然天然存在：见 §3 步骤3 的 `*.lst` 约定（往 `StringHashDumper_Output`
  丢一份 `*.lst` 就能被步骤3 用上）。

## 9. 已知限制与后续建议

- **推理补充还原的收益有硬天花板**：它只能挖出"资源里明文写过名字"的文件。本作实测 60,133 个
  哈希名里，游戏收集 + 挖掘并集 ≈ 57,840（96.2%），剩 2,292 个在游戏资源里**根本没有名字**
  —— 没有信息源，任何推理都补不出来，只能靠 ① 补个后缀让它们"能打开"。

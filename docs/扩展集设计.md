## 1. 目标与非目标

| | 内容 |
|---|---|
| **目标（一期）** | ① 把 `DirectoryHash.log` / `FileNameHash.log` / `MinedNames.lst` / `HashRestore_RecoveredNames.lst` 的成果**合并去重、规范化、压缩留档**成单一档案；② 能对一份解包目录**只读干跑**出成功率；③ 能装进"扩展集库"并按 exe 摘要自动命中；④ 步骤3 直接消费，**免跑游戏**；⑤ **2026-10-15 追加**：页签「扩展集」+ 从独立仓库**只读在线更新**（§14） |

## 2. 硬约束：哈希不可跨作移植（整个设计的地基）

```text
file_hash   = BLAKE2s-256( UTF16LE( 文件名 + 盐 ) )        # 不含目录
domain_hash = SipHash-2-4( UTF16LE( 目录 + 盐 ), key=0^16 ) # 小写 + 结尾斜杠
```

依据：[docs/hxv4/02-资源名与哈希.md](hxv4/02-资源名与哈希.md) §1–§3、
[CxdecRepacker/core/resource_hash.h](../CxdecRepacker/core/resource_hash.h)。

盐 = `mediaName`，来自该作 STARTUP.TJS 的 bootstrap 前缀，**"每游戏可变，不能写死"**。
运行时它被 `HashCore` 读成 `HasherSeed` 并写进 `Log\Universal.log` 的 `Hash Seed:`
（[HashCore.h:93](../CxdecStringDumper/HashCore.h#L93)、[HashCore.cpp:883](../CxdecStringDumper/HashCore.cpp#L883)）；
离线可由静态 Key 提取得到，落在 `ExtractKey_Output\Static\*.json` 的 `hash_domain`
（[CxdecRecover.cpp:510](../CxdecKeyStatic/CxdecRecover.cpp#L510)）。

**三条推论（决定架构）**：

1. **同游戏**（重解包 / 打补丁 / 换封包）：盐不变 → 档案里的 `哈希↔名字` **直接可用** → 这就是"免跑游戏"。
2. **换游戏**：哈希全部不同 → 档案里的哈希**一条都不中**，只有名字还能用（二期撞新作）。
3. 因此档案**必须内嵌「盐 + 目标 exe 摘要」**，加载时**必须先校验**：
   不匹配要**明确报错并拒绝**，绝不出现"看起来有数据、实际一条不中"的静默失效。

### 2.1 匹配规则（加载时）

| 情况 | 判定 | 行为 |
|---|---|---|
| exe 摘要命中 | 最强信号 | 直接用，报告"来源：扩展集 <会社>/<作品>" |
| 摘要不中、**盐一致** | 可能打过补丁/换版本 | 可用，但标注"盐一致、exe 不同"，报告写明 |
| 盐不一致 | 别的游戏 | **拒绝加载**，明确说明"该扩展集属于 <会社>/<作品>，与当前游戏盐不同" |

> **措辞口径（独立验证发现，2026-10-13 补）**：**"盐不同"这句话只在"当前游戏的盐可得"时才可能出现**。
> 若摘要不中**且**拿不到当前盐，报的是"**无法校验归属**"（`LoadFailure::Unverified`），而不是"盐不同" ——
> 两者出路不同（前者可走静态 Key 提取或强行使用；后者只能换档案）。断言必须区分，不能只看关键词。
> 另外：**结构缺失/损坏**（`LoadFailure::Structure`）与"别的游戏"是**两类**，出路完全不同（见 §13.12）。

> 目标 exe 名可能是补丁产物 `<原名>_crack.exe`（步骤1 的补丁流程会改目标）。
> 生成时同时记录**目标 exe** 与**去掉 `_crack` 的兄弟 exe** 的摘要，查找时两者都试。

## 3. 档案格式 `rules.int`

容器**只沿用 [Hxv4p.h:12-26](../CxdecRepacker/hxv4p/Hxv4p.h#L12-L26) 的惯例**（CRC32 多项式、magic/version、flags bit0 = zlib、
**未知 chunk 跳过**），**不追求与 hxv4p 逐字节同构** —— hxv4p 本身是 24 字节头 + 行内 8 字节 chunk 头（没有 chunk 表），
本格式按下面这段布局（2026-10-13 定，实现已按此落地）。压缩用仓库里**已 vendored 的 zlib**
（`CxdecRepacker\third_party\zlib`，`deflate.obj` / `compress.obj` 已编进 `CxdecRepacker.dll`），**不引第三方依赖**；
SipHash 直接复用 `CxdecRepacker\crypto\siphash.cpp`（不另抄一份，避免口径分叉）。

> 两处**有意**与仓库既有口径不同：① `IDENTITY` 里的 exe 摘要用 **SHA-256 大写 hex**（参数仓库 `keystore.h` 用 BLAKE2s 小写；
> 两者是独立仓库，各自自洽即可）；② 空串盐视为**合法**（`saltKnown=true`），与 `Yua::Miner::ReadSalt`（空值=不可用）不同。


```text
头部（20 字节）
  magic       u32   'YXS1'
  version     u16   1
  headerSize  u16   20
  flags       u32   bit0 = payload 经 zlib 压缩
  crc32       u32   未压缩 payload 的 CRC-32
  chunkCount  u32
chunk 表项（每项 12 字节）
  id u16 / flags u16 / offset u32 / size u32     ← offset 相对 payload 起点
payload（可 zlib 压缩）
```

| chunk | id | 内容 |
|---|---|---|
| `META` | 0x0001 | UTF-8，逐行 `key=value`：会社 / 作品名 / 贡献者 / 版本 / 日期 / 留言 / 生成时间 / 工具版本 |
| `IDENTITY` | 0x0002 | 目标 exe（名 + 大小 + sha256）、`_crack` 兄弟 exe 摘要、**盐**（UTF-8 + `saltKnown` 标志，空串是合法值）、来源目录（相对路径）、采集来源清单 |
| `DIRS` | 0x0003 | **规范化目录名**（小写 + 结尾斜杠），UTF-8，`\n` 分隔 |
| `FILES` | 0x0004 | **规范化文件名**（裸名 + 扩展名），UTF-8，`\n` 分隔 |
| `EXCEPTIONS` | 0x0005 | 重算不回去的条目，`大写HEX:名字`，UTF-8 |
| `RULES` | 0x0006 | **预留**（二期 L1 模式层） |
| `STATS` | 0x0007 | 各来源条数 / 去重后条数 / 例外数 / 生成耗时 |

### 3.1 三层结构与"哈希默认不存"

| 层 | 存什么 | 说明 |
|---|---|---|
| **L1 规则/模式层**（二期） | 批量命名规则（如 `voi_%s_%04d`） | 展开成名字，体积比逐条列小几个数量级 |
| **L2 名字层** | 规范化名字（`DIRS` + `FILES`） | 档案主体 |
| **L3 哈希层** | **默认不存** —— 加载时由 `L2 + 盐` 重算；只有重算不回去的进 `EXCEPTIONS` | 省掉 32 字节/条的哈希 |

### 3.2 生成期自校验（白送的保险）

每条都做一次「名字 + 盐 → 重算哈希 → 与采集到的哈希比对」：

- 一致 → 进 L2；
- 不一致 → 进 `EXCEPTIONS` 原样存，**并如实报数**。

好处是双份的：既保证档案里的名字真能复原哈希，又把**归一化口径错误变成自动检测**——
例如目录候选少了"小写 + 结尾斜杠"的归一化，生成时就会大面积落进例外表，
而不是等到撞库命中 0 才发现（详见 §12 限制 1）。

### 3.3 体积估算（按真实量级：60,133 个哈希名文件、`MinedNames.lst` 51,875 条）

| 存法 | 估算 |
|---|---|
| 纯文本 `HASH:name` | ≈ 4.7 MB |
| 二进制（32B 哈希 + 名字） | ≈ 3.0 MB |
| **只存名字 + 盐（本文方案）** | ≈ 1.3 MB，**deflate 后 ≈ 0.6 MB** |
| 再叠 L1 规则层（二期，语音那批） | 还能再降一档 |

**档案不含可读文本视图**（用户 2026-10-13 决定）：档案只出 `rules.int`，体积最优。
"想看"由两处**天然产物**覆盖，产品不需要再出导出按钮：

1. **报告**：会社 / 作品 / 各来源条数 / 去重后条数 / 例外数 / 盐摘要 / 档案大小；
2. **展开产物**：§7 加载时写出的 `StringHashDumper_Output\Extension_<会社>_<作品>.lst`
   本身就是 `HASH:name` 明文，临时产物、可随时删，看/删都不影响档案。

开发与验证要逐条 dump 时，脚手架直接读那份 lst 做断言，**不进产品 UI**。
人工补充名字也**不走"编辑档案"**，而是走既有契约：往 `StringHashDumper_Output` 放一份 `*.lst`，
步骤3 会一并读取（[HashNameRestorer.cpp:476](../CxdecExtractorLoader/HashNameRestorer.cpp#L476)）。

## 4. 生成流程（「生成当前游戏扩展集」）

```text
1) 定盐        优先 Log\Universal.log 的 Hash Seed: → 静态派生（ExtractKey_Output\Static\*.json 的 hash_domain）
               → 都没有：明确报错并中止（与挖掘同口径，绝不静默）
2) 采集        按下表合并去重（运行时采集优先，不覆盖已有）
3) 归一化      目录：\ → /、小写、补结尾斜杠、根域记 /；文件：只取裸名（哈希不含目录）
4) 自校验      §3.2；统计例外
5) 落盘        写 <草案目录>\rules.int（zlib）；同目录另写 info.txt（meta 的只读副本，仅供人看）
6) 报告        各来源条数 / 去重后条数 / 例外数 / 档案大小 / 耗时
```

| 采集来源 | 位置 | 内容 |
|---|---|---|
| 目录映射 | `StringHashDumper_Output\DirectoryHash.log` | `名字##YSig##哈希`（16 位 = 目录） |
| 文件映射 | `StringHashDumper_Output\FileNameHash.log` | `名字##YSig##哈希`（64 位 = 文件） |
| 挖掘成果 | `StringHashDumper_Output\MinedNames.lst` | `HASH:名字`（**只有文件名**） |
| 撞库成果 | `StringHashDumper_Output\HashRestore_RecoveredNames.lst` | `HASH:名字`（目录 + 文件） |
| 同目录其它 `*.lst` | `StringHashDumper_Output\*.lst` | 用户手工放入的对照文件（既有契约） |

## 5. 测试干跑（「测试当前扩展集」）

**只读推演，不动任何文件**（用户 2026-10-13 确认）：

```text
输入  扩展集档案 + 测试来源目录（默认 = 来源目录）
做法  ① 校验盐/exe（§2.1）；② 枚举测试目录里仍为哈希名的 16 位目录段与 64 位文件名；
      ③ 用档案展开出的映射逐个比对，**不复制、不重命名**
输出  可解目录数 / 可解文件数 / 完整路径可还原数 / 成功率 / 未命中明细（可导出）
```

对应图 1 右侧「测试结果（仅供参考）」：来源目录、扩展集来源、测试状态、测试结果、
成功率、扩展集大小、`rules.int` 状态、测试问题、下一步建议、安装位置。

**口径细节（必须与步骤3 完全一致）**：只有「最后两段分别是 16 位目录哈希 + 64 位文件哈希」才算**哈希名文件**；
**直接躺在包根下的裸 64 位哈希文件不算**（步骤3 的 `ResolveHashName` 就是这么判的，`parts[n-2]` 不是 16 位 hex
即整条按"原样搬运"）。成功率分母 = 哈希名文件数。

**展示口径（2026-10-13 定，避免"可解文件数"含糊）**：测试结果面板要**分别**列出三项，不要合成一个"可解文件数"：

| 项 | 含义 |
|---|---|
| ① 可解目录数（去重） | 命中映射的 16 位目录哈希数 |
| ② **文件名可解数**（去重） | 命中映射的 64 位文件哈希数（**可能含"目录未知但文件名已知"的中间态**） |
| ③ **整路径可还原数** | 目录与文件名都命中，能真正落盘的那批 |

**成功率 = ③ ÷ 哈希名文件数**（与步骤3 报告的"还原成功率"同口径）。
断言（E-3）严格判 ③ 与成功率；② 只记录不判 —— 它不影响默认语义下的输出正确性（缺目录的文件默认仍被丢弃）。

**②的"去重"口径 = 按 64 位文件哈希去重**（与内核 `DryRunResult::resolvedFiles` 一致），**不是**按"文件条目数"计：
同一个哈希既出现在"目录已知"又出现在"目录未知"两处时，只算**一条**。所以 ② 与 ③ 只在
"每个命中的文件哈希都至少有一个已知目录落点"时才相等 —— 夹具里恰好有"目录未知但文件名已知"的中间态时
（② 按哈希去重、③ 按条目），两者**可能不等**。

> 这条是 task-2 与 task-3 出现口径分歧（12 vs 13）后由 lead 裁定、并经**独立验证者独立枚举**确认：
> 夹具里 15 个哈希名条目中 13 个的 64 位哈希能查到，但 `928E0FD3…A1E5` 在"目录未知"与"目录已知"各出现一次
> → **按哈希去重 = 12**（面板 5 / 12 / 12 + 成功率 80% 正确）；13 = 文件条目数。见 §11 E-3。

> 这条是 task-1 实现时踩出来的：第一版夹具把"包根下的裸 64 位哈希"当成可还原文件，期望值就写错了（内核是对的）。

> 这条同时是**验收抓手**：干跑成功率必须与"真的跑一遍步骤3"的结果一致（独立枚举对账）。

## 6. 安装与扩展集库

照**参数仓库**（`keys_root`）的既有惯例：[keystore.h:34-62](../CxdecRepacker/pack_static/keystore.h#L34-L62)
——`<根>\<摘要>\profile.hxv4p` + `manifest.txt`（逐行 TSV）+ 内容寻址 + **exe 摘要作主键**。

```text
<扩展集库根>\
  manifest.txt              每行一条 TSV：会社 / 作品 / exe摘要 / 盐摘要 / 档案摘要 / 条数 / 生成时间 / 安装时间 / 来源
  <会社>\<作品>\rules.int    档案本体（**唯一真身**）
  <会社>\<作品>\info.txt     meta 的只读副本：只给人看（浏览库目录时知道这是什么），
                             **工具一律不读** —— 加载只认 rules.int 里的 META chunk
```

- 「安装到扩展集库」= 复制档案 + `upsert` 清单（同一 exe 摘要的旧条目被替换）。
- 「打开扩展集库目录」= 打开库根。
- 库根默认 `<工具目录>\ExtensionLibrary`；工具目录不可写（如装在 `Program Files`）时，
  首次安装弹目录选择框并把选择记进配置（见 §9）。
- exe 路径**只作提示、不作主键**（游戏搬家不影响命中）——与参数仓库一致。

## 7. 消费路径：模式 1「该作扩展集提取」（免跑游戏）

首页功能里 `该作扩展集提取` 是一个**模式**（与 `传统动态模式` 互斥），它把主流程换成另一套三步
（用户 2026-10-13 的 mock 图 3 确认）：

```text
模式 1 · 该作扩展集提取
  步骤1  根据该作扩展集生成静态 Hash 表   →  <工作区>\StaticHash_Output
  步骤2  提取动态 XP3 资源                →  <工作区>\Extractor_Output        （与既有步骤1 同一件事）
  步骤3  用静态 Hash 还原资源名           →  <工作区>\Restored_Extractor_Output
```

对照关系：**模式1 = 传统动态模式里把"跑游戏动态采集"那一步换成"从扩展集生成静态 Hash 表"**。

| 环节 | 做法 |
|---|---|
| 步骤1 生成静态 Hash 表 | 校验档案归属（§2.1）→ 展开 `rules.int` 的名字层 → 用**档案内嵌的盐**重算哈希 → 落 `StaticHash_Output` |
| 步骤3 用静态 Hash 还原 | **还原内核零改动**：只把步骤3 的"映射目录"从 `StringHashDumper_Output` 切成 `StaticHash_Output`（内核本来就只读传给它的目录） |
| 展开产物 | `StaticHash_Output\StaticHash.lst` 是 `HASH:name` 明文 —— 选文本格式的理由**不是**给人看，而是**内核零改动**：步骤3 本来就只读传入目录下的 `*.lst`（[HashNameRestorer.cpp:476](../CxdecExtractorLoader/HashNameRestorer.cpp#L476)）。它是一次性中间产物，可删可重建 |

> 模式1 全程**不启动游戏**：盐来自档案（`IDENTITY` chunk），不需要 `Log\Universal.log`。
> 若目标 exe 摘要与档案不一致（打过补丁/换版本），按 §2.1 的规则处理并如实告知。

## 11. 验收标准（断言清单）

| # | 断言 | 判据 |
|---|---|---|
| E-1 | 闭环免跑游戏 | 合成工作区：先用"旧采集"生成扩展集 → 清空输出 → **不跑游戏**，仅加载扩展集跑步骤3，还原结果与"有原始映射直接跑"**逐条一致**（独立枚举，不采信报告） |
| E-2 | 生成期自校验 | 故意写错归一化（目录不补斜杠/不改小写）→ 例外数**必须**大面积报出，断言必须炸 |
| E-3 | 干跑 == 实测 | 干跑成功率与真实步骤3 结果一致（同一目录、同一档案） |
| E-4 | 坏档案必须被拒 | 盐不匹配 / CRC 错 / 截断 / 版本过高 / 缺 `IDENTITY`：四种都要**明确报错并拒绝**，不许静默 |
| E-5 | 不伪造名字 | 负例名在输出与映射里 **0 次**（沿用既有安全不变式） |
| E-6 | 源目录只读 | 生成 + 干跑 + 消费全程，源解包目录文件数/大小/mtime 摘要不变 |
| E-7 | 幂等 | 同一目录重跑生成：档案字节可复现（同名同盐同内容 → 同一摘要），安装 upsert 不产生重复条目 |
| E-8 | 体积 | 记录实测值（档案大小 / 条数），与 §3.3 估算同量级 |
| E-9 | 大小写与分隔符 | 目录名一律小写 + 结尾斜杠；文件名为裸名；`%EmptyString%` / `/` / `\` 归一化有单测 |
| E-10 | **模式1 ≡ 传统动态模式** | 同一合成工作区、同一份解包目录：模式1（扩展集 → 静态 Hash → 还原）的输出与"传统动态模式（跑采集映射 → 还原）"**逐条一致**（独立枚举对账）；差异只允许出现在"动态采集才有的名字"上，且必须能在报告里解释 |

## 12. 已知限制

1. **目录名只能来自动态采集**：`Miner::MineNames` 只产出文件名
   （[HashNameRestorer.cpp:570-599](../CxdecExtractorLoader/HashNameRestorer.cpp#L570-L599) 只写 `tables.files`），
   所以传统模式里步骤2 采到的目录映射有多少，档案就有多少 —— **挖不出目录名**；
   模式1 的目录覆盖也就只能等于档案里的目录条数。二期目录侧撞库才是补法。
2. **盐变了档案就失效**（换作、改启动脚本、换引擎版本）：必须重新生成。
3. **带密钥哈希不支持**（`FileNameHasherSalt` 非空）：与挖掘同口径，明确报错而不是给错结果
   （[HashNameMiner.cpp:579](../CxdecExtractorLoader/HashNameMiner.cpp#L579)）。
4. 档案**不含资源本体**，不能用来还原"没有名字的文件"；那批只能靠步骤3 的补后缀。
5. 一期不解决"会社撞新作"，跨作复用只有名字层（二期）。

## 13. 已定口径与后续

**2026-10-13 已定（实现依据）**：

1. **工作区 = 游戏目录**（§9），只新增 `StaticHash_Output`；`User\<N>` 多工作区留作独立一轮。
2. **`StaticHash_Output` 只写 `StaticHash.lst`**（`HASH:name`，UTF-8，整份重写，16 位目录在前 / 64 位文件在后、
   按名字不区分大小写排序，与 `HashRestore_RecoveredNames.lst` 的排序口径一致）。
   **不为"人看 / 手补"设计**（用户明确不需要）：不额外落报告文件，条数与来源写进日志与右侧概览面板。
3. **"静态 Hash 表" = 从扩展集离线展开出的映射表（不跑游戏）**，即步骤1 的产物。
4. **档案里默认不写"生成时间/耗时"**（2026-10-13 定）：`Meta::generatedAt` 默认留空 → 不写该字段；
   `Stats` 只存计数，生成耗时只进 `GenerateResult::elapsedMillis`。理由：§11 的 **E-7 要求档案字节可复现**，
   与"把时间戳写进档案"直接冲突，**E-7 优先**。UI 真正给用户生成时填 `generatedAt`（或置 `GenerateOptions::stampGeneratedAt=true`）；
   **验证脚本要测 E-7 就保持默认，别开这个开关**。
   > 2026-10-13 修正（独立验证者发现措辞与 UI 路径矛盾）：**UI 生成路径会写 `generatedAt`**（产品有意的元数据，
   > 不改），所以 E-7 的通过判据是"**除 `META.generatedAt` 外逐 chunk 一致**"；`-StrictBytes`（真逐字节）
   > 只在 `stampGeneratedAt=false` 的**内核级**场景用，**不得**作为 UI 路径的通过条件。
5. 容器布局按 §3 字面实现（20 字节头 + 12 字节 chunk 表），只沿用 hxv4p 惯例；exe 摘要 SHA-256 大写；
   空串盐合法；`allowUnverified` 默认 false（见 §2.1/§3 注释）。
6. `WriteStaticHashMap` 在档案**没有任何名字**时明确报错，不写空表出去（避免"看起来有产物、实际一条不中"）。
7. 库 upsert 的去重键 = **exe 摘要 或 (会社, 作品)**（任一相同即替换旧条目），不产生重复条目。
8. **首页默认模式 = 传统动态模式**（老用户既有行为不变；要用模式1 需自己点）。
9. 干跑**成功不弹模态框**（结果进右侧「制作状态」+ 日志），失败才弹；生成/安装成功仍弹结论框。
10. 「编辑扩展集信息」**只改内存 Meta**：要写进档案必须重新「生成」（内核没有改档案 META 的入口），弹框里已告知用户。
11. 模式1 步骤1 的进度是**阶段级**（加载 → 写表两档），因为内核 `LoadArchiveFromLibrary` / `WriteStaticHashMap`
    没有进度回调；取消在阶段间生效（内核接口如此）。
12. **归属校验被拒时的出口**（已实现）：`!currentSaltKnown` → 弹框给「先做一次静态 Key 提取（离线，不启动游戏）并自动重试」
    /「不校验、强行使用」（显式 `allowUnverified=true`，概览与日志写明"未能校验归属"）；
    **盐不同（别的游戏）→ 内核无论如何都拒绝**（`allowUnverified` 也救不了），UI 只给可操作说明
    （当前盐来源 / 覆写或移开 `Log\Universal.log` 改走静态派生 / 打开日志目录）。
13. 模式1 的「关键目录」只列 `StaticHash_Output` / `Extractor_Output` / `Restored_Extractor_Output`，
    **不列** `StringHashDumper_Output`（免得用户以为模式1 要用动态映射）。
14. **已知问题 P-5（独立验证发现，留待下一轮）**：档案**加载成功、但写静态 Hash 表失败**时
    （例如"空名字"档案），概览的「归属校验」被误报成 **"拒绝加载"** —— 根因
    `YuaExtractMainWindow.cpp:2173` 在写表失败分支**无条件**置 `LastLoadVerdict = Rejected`，
    未区分"加载失败"与"写表失败"；同一段又显示"exe 摘要命中"，自相矛盾。
    修法：把两种失败分开记录。**属罕见路径（只有坏/空档案能触发），不影响功能与输出。**

**二期**：会社合集（多作品档案合并视图 + 按名字重算 + 目录侧 SipHash）、L1 规则层（语音批量命名）、
分享/导入（格式版本 + 校验和）、冲突查看器（同一哈希多名字）、`<游戏目录>\User\<N>` 多工作区。

`rules.int` 的 magic 与扩展名沿用用户 mock 的叫法（`rules.int`）；magic 定为 `'YXS1'`，如与既有工具冲突再改。

## 14. 在线更新与远端扩展集仓库（2026-10-15 定，本轮实现）

把 §1 非目标里的「分享/导入他人扩展集」提前到本期：扩展集用**一个独立的 GitHub 仓库**分发，
工具侧只做**只读拉取**（发现 → 校验 → 入库），不做上传。

### 14.1 为什么单独一个仓库

1. **节奏不同**：扩展集是数据/知识，工具是代码。分仓 = 各自独立发版，工具发版不用拖着几十 MB 数据，
   数据更新也不用重编工具（也就不会每次更新数据都让构建指纹作废、重跑一轮验收）。
2. **格式能直接复用**：索引就是一份 `manifest.txt`（§6 那套 TSV），`ReadManifest` 现成能吃；
   仓库里**没有任何 JSON 解析器**，用 TSV 等于零新解析器。
3. **路径能推导**：远端按 `<会社>/<作品>/rules.int` 放，与 `InstallToLibrary` 的落点规则完全一致。

### 14.2 仓库布局

```text
<repo>/
  index.txt                      ← 索引（见 §14.3）；就是一份 manifest.txt
  README.md
  LICENSE
  <会社>/<作品>/rules.int        ← 档案本体（与 <工具目录>\ExtensionLibrary\<会社>\<作品>\ 同构）
  <会社>/<作品>/info.txt         ← 可选；只给人看，工具不读
```

下载 URL = `<基址>/<会社>/<作品>/rules.int`（会社/作品取自索引行，做 `MakeSafePathComponent` 之后拼接）。

### 14.3 `index.txt` 逐列定义

**与本地 `manifest.txt` 完全同格式**（`ExtensionSet.cpp` 的 `WriteManifest`）：

```text
# 会社	作品	目标exe摘要	兄弟exe摘要	盐摘要	档案摘要	条数	生成时间	安装时间	来源
<会社>	<作品>	<64位大写hex>	<64位大写hex 或空>	<64位大写hex>	<64位大写hex>	<整数>	<自由文本>	<自由文本>	<自由文本>
```

- `#` 开头的行是注释，跳过；字段用 `\t` 分隔；缺列/多列的行**明确报错并点名行号**（不静默跳过）
- **索引里没有"档案大小"和"档案路径"**：路径由 会社/作品 推导，大小以下载后实测为准
- `目标exe摘要` 是**信任根**（见 §14.4 第 4 条），必须非空
- `档案摘要` 必须非空，且必须等于下载到的 `rules.int` 的 sha256

### 14.4 信任链（下载来的东西一律当**不可信输入**）

| # | 要求 |
|---|---|
| 1 | 仅 `https`；不跟随到 `http` 的重定向；连接/发送/接收各自超时；整档体积上限；UA 标注产品名与版本 |
| 2 | 下载后 **sha256 必须等于索引里的 `档案摘要`** —— 这一条把"下到的字节"钉死在索引上 |
| 3 | 解码档案（走内核既有解码路径）→ **magic / version / headerSize / CRC32 / chunk 结构**必须全部通过 |
| 4 | 解码出的内嵌 **`target.sha256` 必须等于索引里的 `目标exe摘要`** —— 拿**索引**当信任根，不拿本机 exe 当根 |
| 5 | 档案**自洽性**：`EXCEPTIONS` 必须为 0；用内嵌盐展开后，`好哈希 → 名字` 的条数必须与 `STATS` 里的目录/文件条数一致（防截断、防名字列表被改短） |
| 6 | 以上任一不过 → **明确报错、丢弃临时文件、本地一个字节都不改**（**含新建的目录**：失败后磁盘必须与调用前逐项一致，**空目录也算**）—— 见下面第 6 条的勘误 |
| 7 | 入库复用 `ExtensionSet::InstallToLibrary`；**同 exe 摘要但档案摘要不同时先给确认**（列出新旧条数/摘要），不静默覆盖 |
| 8 | **绝不自动加载**、**绝不后台联网**：只在用户点「在线更新」时拉一次；入库只写库，用不用仍由「归属校验」（§2.1）把关 |
| 9 | **索引行与档案内嵌 META 的 会社 / 作品 必须一致**（`_wcsicmp` 比，与库自己的 upsert 键同口径）；不一致 → **拒绝**，错误里点名两边。**2026-10-15 独立验证发现后补**，理由见下 |

> **第 9 条为什么要单独列（2026-10-15 独立验证发现）**：
> 之前只把"索引名 ≠ 档案 META 名"**照实显示在 detail 里**就放过去了。验证者实跑证明那样不行：
> 索引写 `IndexSaysThis / AndThis`、档案 META 是 `VictimPublisher / VictimTitle` 时，
> 产品会弹「已新增：IndexSaysThis / AndThis」，磁盘上却落到 `ExtensionLibrary\VictimPublisher\VictimTitle\`，
> 写出的清单行还自相矛盾（名字列来自档案 META、`来源` 列来自索引）。
> 更糟的一路是**覆盖确认框**：它按**索引名**找到"要覆盖的本地条目"报给用户，
> 而 `InstallToLibrary` 覆盖的是**档案 META 名**那个槽 —— 用户确认"覆盖 A/B"，实际被换掉的是 C/D。
> 根因是"安装槽位"这条链路上有两个名字来源（索引 vs 档案 META），必须**在入口就要求它们相等**，
> 让"用户看到的"与"实际落盘的"永远是同一个名字。**索引是信任根，槽位必须可预测。**

> **第 6 条的勘误（2026-10-16 独立验证增量复核发现）**：这句"本地一个字节都不改"**当时并不完全成立** ——
> 建目录失败（例如会社是 `CON`，或 `A:B` 与 `AB` 撞到同一目录）会**留下新建的空目录**，
> 而界面上同一句结论却写着「本地库未被改动（档案没写进库）」。**对用户说了假话。**
> 两件事都要做：① 失败时把**本次调用自己建的空目录**从深到浅删掉，让那句话成真；
> ② **验证侧的目录摘要原先只枚举文件**，对"新建空目录"是**盲**的（所以这个症状一直没被抓到），
> 摘要必须同时覆盖目录，否则这一整族"本地零改动"的判据都名不副实。

> **第 5 条要说清楚它能证明什么、不能证明什么（2026-10-15 纠正）**：
> 档案的 L3 哈希层**默认不存**（§3.1），**里面没有哈希可以对照**。所以"名字 + 盐 → 重算哈希必须回得去"
> 这条自校验只在**生成时**成立（那时手里有动态采集到的哈希）；**校验别人给的档案时根本验不了**——
> 把某个名字改掉，本地没有任何依据能发现。
>
> 因此本设计的**信任根就是索引**：第 2 条证明"下到的字节 = 索引里那一条"，第 3/5 条证明"这份字节是
> 自洽的、没被截断"。**工具不声称能验证"名字对不对"**，也不该在界面上这么说。
> 名字对不对的最终把关仍然是**事实**：归属于本作时（§2.1）用它还原，还原率不对就是不对；
> 以及用户可以对比条数。**要更强的保证只能靠仓库侧签名，本轮不做**（§14.7）。

### 14.5 基址解析与配置

解析顺序（先命中先用）：

1. 环境变量 `YUAEXT_ENDPOINT`
2. `YuaExtract.ini` 的 `[online] base=` —— 优先 `<工具目录>\YuaExtract.ini`；工具目录不可写时用
   `%LOCALAPPDATA%\YuaExtract\YuaExtract.ini`
3. 代码里的默认常量 `kDefaultRepositoryBase`（本轮 `<owner>/<repo>` 先留占位，建好仓库后改一处）

「在线更新」弹窗里可以直接改并回写 ini；弹窗**必须显示当前基址**，否则"点了没反应却不知道在打哪个地址"。

> **为什么基址必须可配置**：`raw.githubusercontent.com` 在国内经常连不上或极慢。这不是锦上添花，
> 是功能能不能用起来的前提（可换镜像 / jsDelivr / 自建）。

### 14.6 失败口径

- 端点不可达 / DNS 失败 / 超时 / 非 200 / 索引格式错 / sha256 不符 / 解码失败 / 自校验有例外 /
  **索引名与档案 META 不一致（§14.4 第 9 条）**：
  **每一种都要有各自明确的措辞**，不许合并成"更新失败"一句
- 任何一种失败，**本地库、库清单、工作区都必须与操作前逐字节相同**（验证脚手架按前后目录摘要判）
- 成功的措辞要能区分「新增」与「更新（覆盖了哪一条、旧档案摘要是什么）」

### 14.7 本轮不做

- 仓库侧写入（不做上传 / 不做 PR 流程），只读拉取
- 增量 / delta 更新（每次都整档下载；扩展集本来就只有几百 KB）
- 冲突查看器（同一哈希多名字）
- 启动时自动检查更新、后台定时检查
- `<游戏目录>\User\<N>` 多工作区

### 14.8 已知取舍

  **必须先改本节并写明理由**，不能只改代码。

## 2. 本轮三项改造（改了什么）

### ① 挖掘改后台线程 —— `CxdecExtractorLoader\YuaRestoreWindow.cpp`

**改造前**：候选挖掘在**界面线程**同步跑数分钟，靠泵消息勉强维持响应 → 用户反馈"开始跑推理补充还原时电脑卡顿"。

**改造后**：

| 机制 | 实现 |
|---|---|
| 进度消息 | `kMsgSupplementProgress` = `WM_APP + 0x504`，lParam = HeapAlloc 的 `{ScannedFiles, Candidates, Hits}` |
| 结论消息 | `kMsgSupplementDone` = `WM_APP + 0x505`，lParam = `new` 出来的 `SupplementOutcome*`（界面线程接管并 `delete`） |
| 线程优先级 | `SetThreadPriority(..., THREAD_PRIORITY_BELOW_NORMAL)` |
| 两段式 | `StartSupplementMining`（界面线程：收第一遍结果 → 打第一遍还原率 → `CreateThread` → 置闸门 → **立即返回**）；`StartPass2`（第二段，由结论消息分支调用：重置任务表 → 起第二遍） |
| 线程体 | `SupplementMiningThreadProc` 只调 `Yua::RunSupplementRestore(context->Tables, options, cb)`；**不碰任何窗口 API、不泵消息**；取消判据 = `StopEvent \|\| context->Closed` |
| 界面侧 | `OnSupplementProgress`（1 秒节流，候选数未变不重复刷）、`OnSupplementDone`（`delete` 载荷 → `join` + `CloseHandle` 挖掘线程 → 清闸门 → `LogSupplementOutcome` → 更新映射条数 → 启动第二遍） |
| 生命周期 | `WM_DESTROY`：`SetEvent(StopEvent)` → join 工作线程 → **join 挖掘线程 + `CloseHandle`** → `DrainUndispatchedPayloads(hwnd)` → 才释放 context；`context->Closed = true` 在 join **之后**写 |
| 载荷回收 | `DrainUndispatchedPayloads` 用消息范围 `[kMsgTaskUpdate, kMsgSupplementDone]` 过滤，只碰本窗口私有消息（不会吃掉 `WM_QUIT`/`WM_PAINT`）；按类型分别 `delete`（结论）/ `HeapFree`（进度、任务更新） |
| 清理 | 删除了不再使用的 `PumpPendingMessages` 与 `PrepareSupplementRestore` |
| 顺带修的两个缺陷 | ① `Pass2Started` 在 `OnStart` 里从未复位 → 同一窗口跑第二轮会静默退化成单遍；② `context->Supplement`（报告那一节）原先只在被删掉的函数里复位，已挪到 `OnStart` |

**闸门仍必须存在**：挖掘进行中 `CheckRunCompletion` 要直接返回。历史 bug —— 挖掘期间 watchdog 反复判定"任务全到终态"，导致提前收尾（`StopEvent` 置位 → 挖掘秒退 → 第二遍永远排队）。`OnStart` 也要拒绝重入（`Running` / `InSupplementMining` 双重判断）。

**两处对原计划的偏离（有意为之，别改回去）**：
1. 结论载荷用 `new (std::nothrow)` / `delete` 而非 `HeapAlloc` —— `SupplementOutcome` 含 `std::wstring`，`HeapAlloc` 不跑构造函数会崩。
2. `DrainUndispatchedPayloads` 顺带回收未派发的 `kMsgTaskUpdate` 载荷（同类潜在泄漏）。

## 3. 关键架构事实（新会话必须知道）

**步骤3 的「推理补充还原」是两遍式**（用户纠正过两次的语义）：

```
Pass 1 普通还原（只用步骤2 收集的映射）
   ↓
挖掘（后台线程，BELOW_NORMAL，分钟级）
   ↓
Pass 2 补漏（只处理第一遍没交付的文件；已交付的直接跳过）
```

- 勾选复选框二 = 上述三阶段；**不勾** = 只跑一遍普通还原，不挖掘
- 挖掘产出的名字并入本次映射表并落盘 `StringHashDumper_Output\MinedNames.lst`（下次直接读，不必重挖）
- **核心安全不变式**：只写哈希验证过的名字，一条都不自己造；负例名结构上不可能进表
- 未还原文件按文件头补后缀（PNG/JPEG/GIF/BM/TLG/OggS/RIFF/fLaC/ID3/MThd/PK/7z + ≥90% 可打印→`.txt` + 兜底 `.bin`）；`PSB` **故意不在魔数黑名单里**
- 输出目录非空时重跑：内核把"目标已存在且内容逐字节相同"当"什么都不做"，`restoredFiles` 不计 → **还原率会显示 0.00%**（幂等语义，不是 bug）。对账必须用清空过的输出目录

**哈希口径**：`file_hash = BLAKE2s-256(key=FileNameHasherSalt(通常空), message=UTF16LE(裸名 + 扩展名 + seed))`，大写 hex；seed 来自 `Log\Universal.log` 的 `Hash Seed:`

### 验证过程中修掉的脚手架问题（产品侧 0 缺陷）

| 问题 | 影响与修法 |
|---|---|
| 断言正则不认**千位分隔符**（`20,012`） | 夹具数字小（无逗号）不暴露，规模档误报"没有还原率行"；数字段改 `([\d,]+)` 后去逗号 |
| 独立枚举只读 `manifest.json` 的 `files` 数组 | 大夹具（>5000 条）**不带该数组** → 枚举出 0/0 误报对账失败；改走 `Get-ManifestFiles`（自动回退 TSV），并把**绝对路径**打进详情自证 |
| 规模档 O(n²) 对账（2 万 × 2 万 ≈ **4 亿次**比较） | 纯内存、磁盘零增长，表现为"假死"十分钟（曾被误判为空转）；改预建字典 O(1) 查找后 **24 秒** |
| 夹具把 `FileNameHasherSalt` / `PathNameHasherSalt` 也填了值 | 产品**正确地**判定"带密钥哈希、拒绝挖掘"，看起来却像功能没实现；改为留空，另配带密钥模板专测降级（S-6b） |

断言侧新增护栏：每段打印 `[assert <ms>] <在做什么>`、大循环带迭代上限（超限判失败而非空转）、脚本末尾统计整脚本与最长 5 段耗时（任一段 >120 秒即判失败）、断言详情限流（规模档 checks JSON 6.5 MB → 14 KB）。
